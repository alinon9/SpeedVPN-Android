# POC TCP/DNS connectivity diagnostics

This is an isolated diagnostic branch. It adds SOCKS5 CONNECT/DNS breadcrumbs and a system DNS button; it does not change the production branch.

## Device test

1. Build/install the debug APK generated by the `UID Detection POC (Real Device APK)` workflow.
2. Clear old logs before reproducing:
   ```bash
   adb logcat -c
   ```
3. Launch `UID Detection POC`, start VPN, and wait for `VPN: CONNECTED`.
4. Tap **اختبار DNS** while the VPN is connected. The button tests Android's system resolver for `google.com`, shows IPv4/IPv6 answers and elapsed time, and logs a bounded 8-second result.
5. Open Google/YouTube/Facebook Lite/X and reproduce the failure. Then collect logs:
   ```bash
   adb logcat -d -v time | grep -E 'SOCKS5_|SYSTEM_DNS_TEST|UID_WORKER|PACKETS=|LOOKUP_FAILS=|SOCKS relay pipe'

   adb shell dumpsys connectivity | grep -i -E 'vpn|dns|privateDns'
   ```
   On Windows, replace `grep -E` with `findstr /I`.

## Interpreting log markers

- `SYSTEM_DNS_TEST_OK`: Android's system resolver returned one or more addresses while the recorded VPN state was active.
- `SYSTEM_DNS_TEST_TIMEOUT` / `SYSTEM_DNS_TEST_FAIL`: the system DNS path failed; compare against the SOCKS5 logs.
- `SOCKS5_DNS_FAIL stage=queue`: the encrypted DNS worker/queue rejected work. DNS now uses four workers plus a bounded 64-entry queue to tolerate concurrent browser lookups.
- `SOCKS5_CONNECT_FAIL stage=dns`: name resolution failed before an upstream TCP attempt; the log should include the target and reason.
- `SOCKS5_CONNECT_ATTEMPT_FAIL` / `SOCKS5_CONNECT_FAIL stage=upstream-connect`: the target was resolved, but the protected physical-network TCP connection failed. Inspect the exception, address family, physical network, and reply code.
- `SOCKS5_REPLY result=OK replyCode=0`: the upstream TCP socket connected and the SOCKS5 request was accepted. If the app still fails, inspect subsequent `SOCKS relay pipe` errors to determine whether forwarding broke after CONNECT.
- `SOCKS_ACCEPT_REJECT` / `SOCKS5_RELAY_SETUP_FAIL`: connection/session admission or worker scheduling failed.

## Concurrency and UID notes

- The relay admits up to 80 SOCKS sessions and has up to 192 relay workers. TCP relays normally use two workers per active session (upload in the handler plus one download worker). The relay worker pool uses a `SynchronousQueue`, so saturation is now logged explicitly rather than silently closing a socket.
- Encrypted DNS previously used a `SynchronousQueue` with only four workers; a burst of more than four concurrent lookups could be rejected. The fix retains four parallel DNS workers and adds a bounded queue of 64 lookups.
- The current native UID hook is **observational only**: `hev_jni_uid_poc_packet` returns `void`, queues tuple lookups asynchronously, and does not block/allow TUN packets based on the resolved UID. Returning UID 0 instead of -1 would create false attribution, not make TCP pass. SOCKS5 itself does not carry Android's originating UID, so CONNECT logs explicitly show UID as unavailable rather than fabricating it.
- This test uses a real device. A successful APK/CI build is not evidence that the apps work on-device; attach logs from a reproduced failure before changing IPv6 or packet-routing policy.
