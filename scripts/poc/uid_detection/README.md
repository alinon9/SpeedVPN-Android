# UID Detection POC — اختبار على جهاز حقيقي

**الفرع:** `poc/uid-detection-test`  
**التطبيق:** شاشة تشخيص مخصصة داخل APK لهذا الفرع فقط. لا تعدّل منطق التطبيق الإنتاجي، ولا تطبّق قرارات حظر.  
**الهدف:** معرفة ما إذا كان `ConnectivityManager.getConnectionOwnerUid()` يعيد UID صالحًا لتدفقات TCP/UDP أثناء مرورها عبر نفق VPN على جهاز فعلي بنظام Android 10+.

## خطوات الاختبار

1. في GitHub افتح **Actions** ثم **UID Detection POC (Real Device APK)** وشغّله على الفرع `poc/uid-detection-test`، أو ادفع commit جديدًا على الفرع.
2. نزّل Artifact باسم `SpeedVPN-POC` وفك ضغطه للحصول على `app-debug.apk`.
3. ثبّت APK على جهاز Android 10 أو أحدث وافتح **فحص UID (POC)**. يجب أن تظهر شاشة التشخيص أولًا؛ لن يبدأ VPN أو native تلقائيًا عند فتح الشاشة.
4. اضغط **بدء اختبار VPN وNative يدويًا** عند استعدادك، ثم وافق على إذن VPN. إذا لم يمنح Android الإذن، ستظهر رسالة ولن يُستدعى native.
5. انتظر تحديث حالة VPN واضغط **ابدأ التسجيل**.
6. افتح Chrome وWhatsApp وYouTube ونفّذ نشاطًا يولّد حركة مرور في كل تطبيق.
7. ارجع إلى التطبيق. كل بطاقة تعرض `packageName`، البروتوكول TCP/UDP، `srcIp:srcPort → dstIp:dstPort`، UID والحالة.
8. اضغط **تصدير النتائج** واحفظ CSV ثم أرسله للفحص. زر **مسح السجل** يحذف النتائج المعروضة.
9. إذا انهار التطبيق، افتحه مجددًا واختر **تصدير Log** و**تصدير Crash** (إذا توفر الملف)، ثم أرفق الملفين في المحادثة. يمكن أيضًا العثور على المسار الظاهر أعلى الشاشة داخل مجلد التطبيق `Android/data/com.speedvpn.app/files/uid-poc-diagnostics` متى أتاح مدير الملفات الوصول إليه.
10. على Android 13+ اسمح بالإشعارات كي يظهر إشعار بمسار ملف الانهيار. تصدير الملفات من داخل الشاشة لا يعتمد على إذن الإشعارات.

## تفسير الحالات

- **MATCH:** أعاد Android UID صالحًا (حتى لو لم يكن ضمن التطبيقات المستهدفة مسبقًا).
- **INVALID:** أعاد Android القيمة `Process.INVALID_UID`.
- **EXCEPTION:** حدث استثناء أثناء طلب UID أو معالجته. يعرض السجل نوع الخطأ ورسالة مختصرة.
- قد يكون تدفق DNS تابعًا لمحلل النظام بدلًا من التطبيق الظاهر؛ سجّل النتيجة ولا تفترض هوية UID مسبقًا.
- التسجيل محدود بآخر 1000 نتيجة في الذاكرة. صدّر النتائج قبل إغلاق التطبيق أو مسح السجل.

## نطاق POC وحدوده

## مسار UID per-flow (تنفيذ POC)

- يقوم مسار حزم HEV بعمل lookup في جدول native قبل أي عبور إلى JNI؛ إصابة الجدول لا تستدعي Kotlin ولا Binder.
- الجدول محدود بـ 4096 تدفقًا، ويستخدم مفتاحًا canonical للخماسية (protocol + عنوان/منفذ الطرفين) بحيث يطابق اتجاهي التدفق، مع idle expiry مدته 30 ثانية.
- التدفقات الجديدة تدخل طابورًا محدودًا بسعة 256 طلبًا. خيط native مخصص بمكدس 1 MiB يتصل بـ JVM مرة واحدة، ويستدعي Kotlin resolver ثم يخزن UID. يمنع pending marker تكرار الطلب لنفس التدفق قبل اكتمال lookup.
- نتيجة UID غير الصالحة تُخزّن مؤقتًا لمدة 750 ms لتجنب استدعاء Binder على كل حزمة فاشلة. انتهاء صلاحية pending هو 10 ثوانٍ.
- المقاييس تظهر كل 1000 حزمة بصيغة `PACKETS / CACHE_HITS / CACHE_MISSES / PENDING_HITS / UNIQUE_LOOKUPS / JNI_LOOKUPS / HIT_RATE / QUEUE_FULL / LOOKUP_FAILS`.
- هذا POC تشخيصي فقط: الحزم لا تُؤخّر بانتظار UID ولا تُحظر. لا تستخدم النتيجة لتطبيق firewall قبل اختبارها على جهاز فعلي.

- لا يدعم هذا الاختبار Android أقل من API 29.
- يلتقط parser الحالي حزم IPv4/IPv6 TCP وUDP الشائعة. تُتجاهل شظايا IPv4 غير الأولى ورؤوس IPv6 الامتدادية.
- لا يغيّر الـ hook الحزم ولا يمنع التطبيقات من الاتصال. النتائج لا تثبت وحدها أن UID filtering صالح للإنتاج.
- يعتمد native hook على نسخة `hev-socks5-tunnel 2.18.0` المثبتة عند commit `d9dca26c7ad0e494492244f0309e80ee583e739e`.

## تشخيص الانهيار

- `SpeedVPN-POC-Log.txt` يسجل مراحل بدء التطبيق والشاشة وVPN ونداءات JNI/native قبل تنفيذها وبعد عودتها.
- `SpeedVPN-POC-Crash.txt` يسجل استثناءات Java/Kotlin غير المعالجة، ويظهر إشعار بمساره عندما تسمح إعدادات الإشعارات.
- الملفات في مساحة تخزين خاصة بالتطبيق حتى لا يحتاج POC إلى صلاحية تخزين واسعة. استخدم زري التصدير لاختيار مكان واضح مثل Downloads.
- `Thread.setDefaultUncaughtExceptionHandler` لا يستطيع اعتراض انهيار native قاتل مثل `SIGSEGV`؛ في هذه الحالة قد لا يتولد ملف Crash منفصل، لكن آخر علامات Log المحفوظة قبل نداء JNI/native ستبقى في ملف Log.
- إذا انهار التطبيق قبل ظهور الشاشة، ثبّت APK الجديد من أحدث تشغيل للـ workflow ثم افتحه مجددًا لتصدير سجل المحاولة الجديدة أو السابقة.
